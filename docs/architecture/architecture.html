1Introduction and quality goals

Tulsi Tiffins POS is a browser-based point-of-sale and inventory system for a small South Indian tiffin café. A cashier rings up an order on a tablet by tapping photo cards, takes cash or UPI and receives an exact receipt; a manager maintains the menu and its photos, receives stock, manages staff and reviews the day’s sales. The system replaces a paper bill book, a calculator and a hand-counted stock list.

This document describes the implemented architecture of release v1.0.0. Requirement identifiers (FR-xx, NFR-xx, TR-xx, BR-xx) are unchanged from the Phase 1 baseline so that every decision can be traced back to the requirement that motivated it.

1.1 Quality goals

The three quality goals below drive every architectural decision in this document, in this order of priority.

3System scope and context

Figure 1 fixes the system boundary. Two human roles use the system; the Manager role is a specialisation of the Cashier role, so a manager can also ring up sales (FR-05). The customer’s UPI app is the only external party: it scans a static QR code generated by the system, and the cashier confirms receipt manually (FR-28). The method is the same for every concern: derive selection criteria from the requirements, list the realistic alternatives, rate each against the criteria, and record the deciding reason.

Summary of the strategy

The stack is chosen around one hard problem: a sale must be atomic and must never oversell. PostgreSQL provides the guarantees (locks, CHECK, NUMERIC, sequences), SQLAlchemy makes the transaction explicit, FastAPI and Pydantic keep the boundary validated and typed, and a strictly typed React client keeps the contract honest at build time. Everything else — Docker, Render, Neon — is chosen to deploy exactly that, for free, with one command.

5Building block view

5.1 Level 1 – the whole system

The system consists of three building blocks. The browser loads the SPA, which reaches the API only through two interfaces: the JSON REST API under /api and the photo endpoint under /media. Only the API talks to the database. In both deployments a proxy (nginx locally, Render rewrite rules in the cloud) serves SPA and API under one origin.

Building blockResponsibilitySource
Web front endFive screens (Login, Register, Inventory, Orders, Staff); holds only UI state; all data via the API.frontend/src (TypeScript, strict)
APIAuthentication, authorisation, validation and all business rules; the only writer of data.backend/app (Python 3.11)
DatabasePersistent state, row locks, constraints, bill-number sequence, product photos.backend/alembic/versions

5.2 Level 2 – backend layers

The API is strictly layered (NFR-16). Routers are thin HTTP adapters; services own every business rule and are the only code that opens transactions; models are only the mapping to tables. Services never import FastAPI — they raise domain errors that app.main translates into HTTP status codes and readable messages (NFR-13). The rule “no ORM query in any router” is checked in review; routers import model classes only as type hints.

5.3 Level 2 – front end

The router wraps manager-only screens in a RequireManager guard — a convenience for the user, not a security boundary, because the API enforces every role on the server (NFR-11). All server data flows through TanStack Query and a single API client that attaches the JWT and turns error responses into readable messages. types.ts mirrors the Pydantic schemas, so a changed field breaks the build rather than a receipt.

6Runtime view

6.1 Ringing up a sale (the critical scenario)

The sale is the one scenario where a design error would cost the café money, so it is implemented exactly once, in services/billing.py. Figure 5 shows its message sequence. Three details make it safe:

  • Lock before read, in a fixed order. All product rows of the basket are locked with SELECT … FOR UPDATE in ascending id order. Two tills selling the last dosa queue on the same row lock; the second sees stock 0 and is rejected. Because every transaction locks in the same order, two overlapping baskets cannot deadlock.
  • Check everything before writing anything. Stock for every line, archived items and short cash are all checked before the first INSERT — and before the bill number is taken, because a PostgreSQL sequence is not rolled back. (This last point was a defect found in Phase 3: short cash used to consume a bill number; it is now fixed and covered by a regression test.)
  • One commit. Bill, lines with copied unit price, payment, one SALE stock move per line and the stock decrement are committed together; any exception rolls back all of it. The CHECK constraint remains as a backstop and is mapped to 409, never 500.

6.2 Other scenarios

ScenarioBehaviour
Log inThe login screen lists active staff names (GET /api/users/pin-targets); the user taps a name and enters a 4-digit PIN; the server verifies it with bcrypt and returns a JWT valid for one 8-hour shift. A wrong PIN returns 401 without saying which part was wrong.
Receive stockThe manager taps “+” on an item; the API inserts a RECEIVE move with a positive amount and updates the cached stock in the same transaction. The sign comes from the reason, so a negative “receive” cannot exist.
Change a priceOnly the product row changes. Old bills are unaffected because each bill line holds its own copy of the unit price (FR-25).
Deactivate staffThe flag is set; the user’s next request fails with 401 because the role is re-read on every request. Deactivating the last active manager is refused.

7Deployment view

The same container images run in two environments. The local installation is the reference required by the brief (docker compose up); the cloud deployment makes the front end directly accessible for evaluation. The application code is identical in both — only configuration differs, and all of it comes from environment variables.

7.1 Cloud – Render and Neon (live instance)

  • Infrastructure as code: render.yaml (a Render Blueprint) defines both services; Render redeploys automatically on every push to main.
  • Start-up: the API container runs alembic upgrade head, then the idempotent seed, then uvicorn on the port Render assigns.
  • Database: Neon runs PostgreSQL 18; the local stack runs 16. The full test suite was run against both versions with the same result (120 passed).
  • Free-tier behaviour: the API sleeps after 15 minutes without traffic; the first request then takes about 30–60 s. Render’s disk is ephemeral, which is why product photos were moved from a file volume into PostgreSQL (migration 0002).

9Cross-cutting concepts

ConceptImplementation
Authentication4-digit PIN verified against a bcrypt hash; there is no plaintext PIN column. Signed HS256 JWT, 8 h lifetime; the secret is generated by the host and never committed.
AuthorisationFastAPI dependencies get_current_user / require_manager on every protected route; the user and role are reloaded from the database per request. Missing or invalid token → 401, wrong role → 403.
Public endpointsDeliberately public: POST /api/auth/login, GET /api/users/pin-targets (names and roles of active staff for the login screen — never PINs), GET /api/health (host health check) and GET /media/products/{name} (photos, because an <img> tag cannot send a bearer token; names are random 128-bit UUIDs). All other routes require a token — 27 automated RBAC tests check this.
Input validationEvery body and query goes through a Pydantic model (NFR-10): positive quantities, 4-digit PINs, cash must carry a tendered amount, UPI must not.
File uploadsContent type and filename are ignored; the bytes must decode as PNG, JPEG or WebP; the image is re-encoded from pixels (removing EXIF and polyglot payloads), scaled to 900 px and stored under a generated UUID. SVG is refused.
Error handlingServices raise domain errors (NotFoundError, ValidationError, ConflictError, InsufficientStockError); one handler maps them to HTTP codes with sentences such as “Insufficient stock: only 3 left” (NFR-13).
MoneyAll arithmetic in services/money.py with Decimal and ROUND_HALF_UP; a release-gate test asserts that no float ever reaches a money column.
ConfigurationTwelve-factor style: database URL, JWT secret and lifetime, UPI ID, GST rate and seeding all come from environment variables (.env.example, render.yaml).
Schema evolutionAlembic migrations only; the app never creates tables itself (NFR-17). Migrations run automatically on container start.
Test dataAn idempotent seed creates a realistic café: 12 menu items in 4 categories with prices and stock, and 3 staff accounts — no dummy text.

10Architecture decision records

The technology choices are covered in Section 4. The following design decisions within that stack each had a realistic alternative; they are recorded in short ADR form (context → decision → consequence).

ADRDecisionAlternative rejectedRationale and consequence
01Pessimistic row locks during the saleOptimistic locking with a version columnOptimistic locking would make a busy counter retry sales at checkout; a short lock is invisible to the user. Consequence: sales of the same item are serialised (milliseconds).
02Lock rows in ascending product id orderLock in basket orderTwo baskets with overlapping items in opposite order could deadlock. Fixed ordering removes the possibility.
03Append-only ledger + cached stock columnCompute stock as SUM(delta) on every readFull audit trail and a fast menu query; the cost is keeping the mirror in step, which is done in the same transaction and reconciled by a test.
04Validate everything, then take the bill numberTake the number firstSequences ignore rollback, so taking the number first leaves gaps in an audited series. Phase 3 fix extended this to short cash.
05Decimal end to endFloat maths, round for display₹0.05 cannot be represented exactly in binary floating point; rounding errors would accumulate across a day.
06Copy unit price onto each bill lineJoin bill lines to the current priceReceipts are historical records; a price change must not rewrite them (FR-25).
07Archive products, never deleteHard delete with cascadeOld bills keep their items; the menu stays clean (FR-14).
08Re-read role from DB per requestTrust the token’s role claimDeactivation is immediate. Cost: one indexed query per request.
09Domain errors in services, HTTP mapping in one placeRaise HTTPException in servicesServices stay independent of the web framework and testable directly; messages are consistent.
10Store photos in PostgreSQL (Phase 3)File volume; object storage (S3, Vercel Blob)The free cloud host wipes its disk on restart; object storage would add a third service and credentials. A photo now commits in the same transaction as the product’s photo_url. Cost: about 50–150 KB per photo in the database, acceptable for a menu of tens of items.
11Tests on a real PostgreSQLSQLite in memoryOnly a real database proves the locks and the CHECK constraint. Cost: the suite needs Docker and takes about 110 s.
