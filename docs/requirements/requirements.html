1Purpose, baseline and how to read this report

This report closes the requirements loop of the project. Phase 1 fixed the requirements before any code was written, as the Waterfall model requires, and prioritised them with MoSCoW. This report takes that baseline unchanged – the identifiers and wording are those of the Phase 1 report – and states for each requirement whether release v1.0.0 meets it, where it is implemented and which test proves it.

1.3 Where the evidence comes from

  • Automated tests: 120 pytest tests in backend/tests/, run against a real PostgreSQL database (16 locally, 18 in a second run matching the cloud database). They are cited as module::test name, for example billing::tc03 for test_billing.py::test_tc03_insufficient_stock_is_rejected_and_nothing_is_written. All 120 pass; the full suite takes about 112 s.
  • Code: backend services in backend/app/services/ (the only layer with business rules), front-end screens in frontend/src/screens/.
  • Live smoke test on 28 Oct 2026 against https://tulsi-web.onrender.com: 401 without a token, 401 for a wrong PIN, 403 for a cashier on a manager route, a cash sale (bill 1042, ₹84.00, change ₹416.00), a UPI sale (bill 1043, ₹42.00), an oversell rejected with 409 “only 57 left”, photo upload and delete, and the daily total (₹126.00).
  • Reviews: code-structure and schema inspection, where Phase 1 names a review as the measurement method.

The architecture behind these requirements – components, data model, the atomic sale and the deployment – is described in the separate Architecture Documentation v1.0.0. Technical-debt identifiers (TD-01…10) are the same in both documents.

2Actors and use cases

Two human actors use the system. The Cashier rings up sales and takes payment; the Manager can do everything a cashier can and also maintains products, stock and staff and sees the daily total. Both sign in with a four-digit PIN. The Customer is a secondary actor: they pay, and for UPI scan the café’s QR code with their own phone, outside the system.

Role enforcement is a server-side rule (NFR-11): a hidden tab in the user interface is only a convenience. Every manager-only use case returns HTTP 403 for a cashier token, which is tested for every manager endpoint (Section 3, FR-04).

7Changes to the requirements since Phase 1

No requirement was removed or re-prioritised. The changes below refine how a requirement is met; each was made during implementation when a test or the deployment showed that the Phase 1 wording left a gap.

AffectsChangeReason
FR-24The bill number is taken only after every check, including stock and the cash amount.PostgreSQL sequences are not rolled back. Taking the number first left gaps for rejected sales; a Phase 3 test showed that short cash still caused one (bill 1044 instead of 1043).
FR-27A cash payment below the total is rejected with HTTP 400 and nothing is written.The Phase 1 criterion described only the change calculation, not the short-payment case.
FR-11The last active manager cannot be deactivated or demoted, and nobody can deactivate themselves.A staff test showed the café could lock every manager out.
FR-11, NFR-11Role and active flag are re-read from the database on every request, not trusted from the token.A deactivated or demoted user must lose access at once, not after 8 hours.
FR-12, FR-19Managers can upload a product photo; the photo is stored in PostgreSQL (migration 0002), decoded and re-encoded on upload.The Register shows photo cards as in the prototype. The free cloud host wipes its disk on restart, so a file volume would lose photos; re-encoding blocks disguised files (NFR-10).
FR-29Cashiers can also read the bill history (receipt reprint); only the daily total is manager-only.Phase 1 already named both actors for FR-29; the manager-only part is FR-30.
NFR-07Three routes besides login are public: the staff name list for the login picker, /api/health and product photo files.The login screen must list names before anyone is signed in; the host’s health check has no token; photos are loaded by <img> tags, which cannot send a token. None of them returns PIN hashes or sales data (auth::pin_targets_never_leak_hashes). Names on the login screen: TD-07.
NFR-14Added a cloud deployment (Render + Neon) next to Docker Compose.The final submission needs a working link. Same Dockerfiles; configuration only through environment variables.
Phase 1 Table 8Front end in strict TypeScript instead of JavaScript.Shared types make a UI/API mismatch a build error (supports NFR-15).

9Glossary

Terms from the Phase 1 glossary (Table 11), extended with terms introduced during implementation (marked ⁺).

TermDefinition
ACIDAtomicity, Consistency, Isolation, Durability – the guarantees of a database transaction, so a bill and its stock changes commit or roll back as one unit.
AlembicMigration tool for SQLAlchemy that version-controls changes to the database schema.
Archive (product)Deactivating a product so it disappears from the Register but stays on historical bills; products are never deleted.
Bill / OrderA completed sale: line items, subtotal, GST, total, payment and a unique bill number.
Bill lineOne item on a bill, storing quantity and the unit price at the time of sale.
Blueprint ⁺Render’s infrastructure-as-code file (render.yaml) that defines the cloud services of the application.
CashierCounter staff role: Register, payment and bill history, but no product, stock or staff management.
Cold start ⁺The delay when a sleeping free-tier service is woken by the first request (about 30–60 s).
Decimal ⁺Python’s exact decimal number type, used for all money; stored as NUMERIC(10,2).
Docker ComposeTool that runs front end, back end and database as linked containers with one command.
FastAPIPython web framework used for the REST API, with built-in validation.
GSTGoods and Services Tax – 5 % on the subtotal, rounded half-up to two decimals.
JWTJSON Web Token – signed token issued at login and sent with each request to prove identity and role.
Ledger (stock ledger)The append-only stock_moves table, the single source of truth for every stock change.
ManagerOwner/manager role with full access: products, inventory, staff, totals and the Register.
Migration ⁺A numbered Alembic script that changes the schema (0001 initial schema, 0002 product photos).
MoSCoWPrioritisation: Must have, Should have, Could have, Won’t have this time.
Neon ⁺Managed PostgreSQL service hosting the cloud database.
POSPoint of Sale – where an order is rung up and paid; here, the Register screen.
PostgreSQLThe relational database, chosen for ACID transactions and row-level locking.
Pydantic ⁺Python library that validates every request body and query against a typed schema.
RBACRole-Based Access Control – permissions by role, enforced on the server.
ReactJavaScript library used to build the single-page front end, written in TypeScript.
Release gate ⁺A test that must pass before a release: the concurrency and rollback tests in test_billing_gates.py.
Reorder levelPer-product threshold at or below which a low-stock badge is shown.
Row-level lockingDatabase mechanism (SELECT … FOR UPDATE) that serialises concurrent updates to the same product row.
Sequence ⁺PostgreSQL counter object (bill_no_seq) that issues bill numbers; values are not returned on rollback.
SPASingle-Page Application – loads once and updates views without full page reloads.
Stock movementOne immutable ledger entry: quantity change, reason (OPENING, RECEIVE, REMOVE, SALE), user, time and optional bill.
Technical debt ⁺A known shortcut or gap, recorded with an ID (TD-xx) and a remedy.
Traceability ⁺The link from a requirement to the code that implements it and the test that verifies it.
TypeScript ⁺Typed superset of JavaScript; under strict mode a type mismatch fails the build.
UPIUnified Payments Interface – India’s real-time payment system; here used through a static QR code.
Waterfall modelProcess with sequential phases (requirements, design, implementation, testing, deployment), each completed before the next.
