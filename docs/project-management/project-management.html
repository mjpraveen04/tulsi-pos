1Project profile in brief

The full project profile – background, objective, scope, target users, organisation and risks – is the Phase 1 report (MysoreJagannath-Praveen_10251728_PSE_P1_S.pdf, in this folder). This report records how the project was actually run against that profile.

ItemPhase 1 baseline
ObjectiveOne affordable, touch-friendly web application that unifies register, inventory, orders, staff and payments for a small café, so that every sale updates stock correctly and is recorded with a full audit trail.
Scope (MVP)PIN login with two roles; staff management; products and an append-only stock ledger; a Register that cannot oversell; atomic billing; cash and UPI (static QR); searchable order history.
Out of scopeUPI gateway with webhooks, supplier purchase orders, analytics dashboards, table and reservation management (FR-F1…F4).
MethodologyWaterfall: conception, design, implementation, testing, deployment; requirements frozen with MoSCoW before coding.
OrganisationSingle developer in all roles – project lead, requirements analyst, developer, tester, technical writer; tutor review at the end of each phase.
Planned end25 September 2026
BudgetNo funding: free and open-source tools, free hosting tiers.

2Schedule – plan against actual

The plan had nine work packages from 4 August to 25 September 2026. The implementation and test work packages WP1–WP8 were finished early, by 13 August, for the Phase 2 submission. Deployment and final documentation (WP9) were planned for 20–25 September but were done on 26–28 October, after a break of about two months with no development. The release therefore came 33 days after the planned end.

4Scope management

The scope was fixed in Phase 1 with MoSCoW. The rule was that a new idea is logged for a later phase, never built mid-project; it was also written into the repository’s build rules (CLAUDE.md, “Scope discipline”).

MeasureResult
Won’t-have items built0 of 4 – no UPI gateway, purchase orders, charts or table management.
Requirements dropped0 of 30 functional, 0 of 18 non-functional.
Requirements delivered29 of 30 functional requirements fully met (FR-16: 2-second target not measured); 14 of 18 non-functional met.
Changes during the projectNine refinements, all additive – for example short-cash rejection, the last-manager guard and photo storage in the database. Listed with reasons in the Requirements and Traceability Report, Section 7.

6Quality management

7Configuration and release management

  • Repository: one public GitHub repository with code, Docker and cloud configuration, tests and all documentation (docs/). Work is committed directly to main – appropriate for a single developer – and every push to main redeploys the hosted application.
  • Versioning: semantic versions. The documents carry the same version as the software; v1.0.0 is marked by the git tag v1.0.0 and a GitHub release, which freeze code, diagrams and documents together.
  • Database schema: versioned Alembic migrations (0001, 0002); never changed by hand.
  • Diagrams as code: PlantUML sources in docs/architecture/diagrams/, rendered to PNG for each release.
  • Submission copy: the code zip in 04-Implementation is generated from the tag with git archive v1.0.0, so it is identical to the GitHub repository.

Lesson: git was introduced only after the implementation, so the versions v0.1.0 and v0.2.0 exist as document versions but not as commits or tags. In a next project the repository would be created on day one and every phase tagged.
